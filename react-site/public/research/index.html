你还记得「方案 B」吗？AI 编程助手在长会话中的回头引用与开发者理解

研究计划 · 草稿 v0.1 · 2026-09-27

作者：梁悦

一句话摘要

AI 编程助手在长会话里会给东西起名字（「方案 B」「不动 schema」「探针」），之后再提到时只用这个名字。模型能看到全部上下文，开发者却记不住。本研究测量这种写法让开发者的理解损失多少，检验"把远处的引用说全"和"按工作记忆规则重排回复"两种改法能补回多少，并估计它们的阅读成本。

1. 问题

开发者和 Claude Code、Cursor 这类 AI 编程助手的会话越来越长。我在自己的 180 个 Claude Code 会话里看到，超过一半（56%）的回复发生在上下文超过 15 万 token 的时候，最长的超过 60 万 token。一个会话常常跨好几个小时，中间开发者还会切去做别的事。

在这种会话里，AI 的回复经常引用很早以前出现的东西，例如：

先确认回退点还在，然后部署宽限期。线索 3 的客户端锁记到下个 App 版本里。

对模型来说，「回退点」「线索 3」就在上下文里，随时可以查到。对开发者来说，这些名字可能是一小时以前、几万字以前出现的。读不懂的直接后果是：开发者要么往上翻很久，要么照着一个没弄懂的指令去做。

人和人说话时会处理这个问题。刚提过的东西说"它"；隔了很久再提，会说"上周说的那个不肯修热水器的房东"。语言学把这叫作可及性：说话人按对方还能不能想起来，选择说得多完整（Ariel 1990；Givón 1983）。本研究要检验的是：AI 编程助手是否缺少这种调整，缺少它的代价有多大。

2. 相关工作

文献检索由三个方向同时进行，共约 100 次检索，最接近的论文都打开摘要或全文核对过。详细记录见项目里的 notes/ 目录。

  1. 指代与可及性。 人选择指代形式时会考虑听者还记不记得：隔得越远，越倾向用完整说法（Ariel 1990；Givón 1983；Aina 等 2021 在人类文本里也观察到距离的强烈影响）。
  2. 概念约定。 对话双方会就"怎么称呼一个东西"形成约定（Brennan & Clark 1996），约定被打破时听者要付出理解成本（Metzing & Brennan 2003）。本研究的现象可以这样表述：AI 单方面定下了约定（给东西起名字），人却没有真正记住它。近期研究发现，在指代游戏里 LLM 不会像人那样越说越简短（Hua & Artzi 2024；Hua 等 2025），这和我们观察到的"直接用名字"方向相反，论文需要解释编程会话为什么不同：名字是 AI 自己起的，不是双方协商出来的。
  3. 大模型的指代与共同知识。 Wu 等（INLG 2025）发现 LLM 的指代选择与人类不同，但文本最多 3 句，测不了长距离。Shaikh 等（NAACL 2024）发现 LLM 的确认和澄清类话语比人少约 77.5%，会默认双方已有共同知识；他们的 ACL 2025 论文发现 LLM 主动澄清比人少 3 倍。这两项研究测的是话语行为，不是指代形式，也没有测读者理解。
  4. 去语境化与术语解释。 Choi 等（TACL 2021）把句子改写成可以单独读懂，用户研究比较了"改写句 / 原句 / 整段"，和本研究的三组很像，但只问了偏好。Newman 等（EMNLP 2023）的评估是两位作者排序。ScholarPhi（Head 等，CHI 2021）为论文作者自造的术语提供悬浮定义，读者答题更快，这是和本研究最接近的 HCI 先例，但它针对论文、按需显示，不考虑距离。
  5. AI 编程助手的真实使用。 大规模会话分析（Tang 等 2026，2 万多个会话；SWE-chat）的分类里，都没有"看不懂 agent 的措辞"这一类。Wang 等（arXiv 2026-09）分析了 8.4 万条通用聊天里的"看不懂"信号，但不是编程场景，也没有区分原因。Claude Code 的 GitHub issue #86205 里有用户反馈 Claude 会"给东西起名字，而不是用真实的变量名"。
  6. 为注意力困难的读者重排回复。 Adapt AI（ACM Creativity & Cognition 2026）为注意力困难的用户重排 LLM 回复，只访谈了 10 人，没有对照组，也没有理解测试。本研究 C 组使用的规则来自开源的 i-have-adhd skill（GitHub），它还没有被评估过。借用"路缘坡道效应"（Blackwell 2017）的思路，本研究检验这套规则对一般开发者是否也有帮助。

目前的空白： 没有找到测量 AI 助手回头引用是否随距离调整的研究，没有找到用理解题、句子标记和"以为懂了"指标测读者的去语境化研究，也没有找到按距离决定是否补全的方法。检索用的是通用搜索、arXiv、ACL Anthology 和 Semantic Scholar；ACM DL 里 CHI '26、UIST '26 的全文检索还没做，投稿前需要补上。

3. 研究问题与假设

RQ1： AI 编程助手给一个东西起了名字（比如"我叫它金标准测试"），隔了很久再用这个名字时，会不会像人一样重新解释一句？

  • H1： 不会。人说话时，隔得越久，提到同一个东西会说得越完整；AI 的说法不随距离变化，隔 0 字和隔 8 万字，它重新解释这个名字的比例差不多。
  • 怎么检验： 实验一（5.1 节）。在"起名字"和"最后提问"之间插入不同长度的其他对话，其他内容不变，让模型写最后一条回复，看它有没有解释这些名字。

RQ2： 这种写法让开发者损失多少理解？补全引用能补回多少？

  • H2a： 即使开发者刚读完整段对话，他们在远引用题上的正确率仍然低于只读"补全版"回复的开发者。换句话说，把引用说全，比让人记住前文更可靠。
  • H2b： 只读"原版"回复的开发者，有相当一部分会答错远引用题，却没有把对应的句子标成看不懂，也就是"以为懂了"。

RQ3： 按工作记忆规则重排回复，能不能在补全之外再带来帮助？

  • H3： 在信息相同的前提下，"规则版"（先写下一步、编号、结尾写现状）比"补全版"在行动题上的正确率更高，或者阅读时间更短。

RQ4（原因，后续研究）： 这种写法是否来自训练时的打分方式？

  • H4： 标注者带着完整对话打分时，会偏好简短引用；只看回复本身打分时，会偏好完整说法。本计划不检验 H4，只作为后续方向。

4. 已有的初步证据

以下数据来自我本机的 Claude Code 会话记录，只做本地统计，原文不外传。

  1. 数据规模。 180 个会话，1890 条含中文的最终回复。上下文长度取自 API 返回的真实 token 数。
  2. 中文表面质量没有变差。 随上下文变长，平均句长、翻译腔词频、英文夹杂比例基本不变。
  3. 回头引用的解释比例不随距离上升（与 H1 一致，但方法粗，见第 5 条）。 在 1354 次回头引用中，AI 在引用处顺手解释的比例，2000 字以内是 3.1%，5 万字以上是 4.0%；相隔 6 小时以上的引用只有 1.1%。这个自动判断方法比较粗，结论需要人工标注确认。
  4. 盲标 100 条（近 50、远 50）。 标注由 AI 完成，标注时看不到距离。只看这段就能懂的比例：近的 82%，远的 72%，差异在这个样本量下不显著。43% 的引号内容是界面文字（按钮名、Tab 名），这类不依赖对话记忆。真正的问题集中在 AI 自己起的名字上：这一类有一半只看这段读不懂。
  5. 在真实记录里自动识别"起名字"，噪音太大。 我先后试了两种自动方法。放宽到"引号里的新词"之后，能找到 1513 次回头引用，重新解释的比例在各个距离上都只有 1%–4%；但抽查 20 条远距离引用，真正是"AI 起的名字"的只有 5–6 条，其余是普通引号、术语或同一个词碰巧重复。所以这组数字不作为证据，H1 改用控制实验来检验。
  6. 局限。 数据只来自一个用户、主要是一个模型（claude-opus-5）；第 4 条的标注正在由人抽检 20 条。

这些证据只能说明现象存在、值得做实验，不能替代实验。

5. 实验设计

本研究包括两个实验：实验一检验 H1（模型会不会按距离调整），实验二检验 H2、H3（开发者的理解）。两个实验用同一批材料。

5.1 实验一：控制距离的生成实验

  1. 做法： 取材料里的对话，在 AI 起完名字之后、开发者最后提问之前，插入 0、2 万、8 万字的其他开发对话（改 README、修样式这类无关小任务），然后让模型写最后一条回复。距离是唯一变化的量。
  2. 模型： 先用 Claude Code（命令行无工具模式，关掉所有用户自定义设置），之后加入 Codex 等其他模型。
  3. 怎么判断"解释了"： 每个名字的定义是已知的，比如「不动 schema」的定义里有"没有备份、没法回滚"。回复里提到这个名字的那一句如果包含定义里的关键词，就算解释了。这套规则用人工逐句阅读核对过。
  4. 预测： 如果 H1 成立，三种距离下解释的比例没有明显差别。作为对照，还会加一个条件：在提示里告诉模型"开发者离开了两个小时刚回来"，看模型在被明确提醒时能不能调整。这个对照也决定了改进方法是否可以只靠提示来做。

预实验结果（2026-09-27，Claude Code 默认模型，4 段材料，共 34 次生成）：

插入的距离回复数名字被解释的比例
0 字1536/56（64%）
2 万字1435/52（67%）
8 万字1436/53（68%）
  1. 支持 H1： 距离从 0 增加到 8 万字，解释的比例基本不变。
  2. 但和原来的设想不同： 即使距离为 0，模型也会解释约三分之二的名字，并不是总用光秃秃的名字。没被解释的集中在少数几个名字上（例如「不动 schema」16 次里只解释了 1 次，"双跑"被判为 9 次都没解释）。
  3. 测量的已知问题： 规则只认同一句里的解释，解释写在下一句时会漏判（人工抽查发现"双跑"至少有 1 例属于这种情况）。正式实验会改成"同一句或下一句"，并用人工标注核对。
  4. 对实验二的影响： 最初的 A 版把所有名字都写成光秃秃的，比真实情况极端。已改为用模型真实生成的回复作为 A 版（见 5.2）。
  5. 局限： 对话是作为一整段文字放进提示的，不是真正的多轮会话；只测了一个模型。下一步加入"开发者说自己离开了两小时"的对照条件，以及 Codex 等其他模型。

5.2 实验二的材料

用真实会话做材料有两个问题：内容涉及隐私，而且看不懂可能是因为不懂代码，分不清原因。所以我改用编写的材料，每段只改一个变量。

每段材料是一段 17–21 轮的开发者与 AI 编程助手的对话，模仿 Claude Code 会话，只保留文字，不放工具输出。对话中 AI 会给 4–5 样东西起名字，最后一条回复会再用到它们。目前写好 4 段：

编号场景AI 起的名字（举例）
02记账 app：首页提速、加收藏功能不动 schema、跨月测试、临时存法、开关
03排查用户偶尔被踢下线线索 1/2/3、探针、回退点
04运费计算从 JS 重写成 TS金标准测试、那 17 单、顺序规则、双跑
05Next.js 14 升级到 15绿线、冻结清单、兼容层

最后一条回复写三个版本，事实完全相同：

  • A 原版（540–680 字）：Claude Code 默认模型读完同一段对话后真实写出的回复，原样使用，只按行切分，一个字没改。
  • B 补全版（比 A 长 0–23%）：只把 A 里没解释的回头引用说全，其他句子一字不改。
  • C 规则版（540–620 字）：B 的内容按 i-have-adhd skill 的规则重排：先写下一步，中间编号，结尾写现在的状态，并去掉结尾的客套句。

A 对 B 只差引用是否补全；B 对 C 只差结构。这种"所有条件都从同一条真实回复增删得到"的做法参照 Kim 等（CHI 2025）。

测试题和对照题。 模型并不会漏掉所有解释，所以每道远引用题都标明它考的名字在 A 里有没有被解释：没解释的是测试题（4 段共 9 道），解释了的是对照题（共 8 道）。只有测试题在 A 和 B 之间应该有差别，对照题可以检验参与者是否认真阅读。框架升级那一段 A 已经把所有名字都解释了，B 和 A 完全相同，只作为对照材料；下一批材料会挑选测试题更多的场景。

预实验后再写 4 段，正式实验共 8 段。

真实度盲测。 编写的材料要足够像真实的 AI 回复，结论才能推广。做法：从已经过隐私审查的真实回复里挑 8 条长度相近的，和 8 条材料的 A 版打乱在一起，请经常用 AI 编程助手的开发者逐条判断"真实的还是编写的"。判断正确率接近 50%，说明材料足够像；明显高于 50%，就要根据他们指出的破绽修改材料。

5.3 分组与分配

组看到什么代表的情况
1完整对话 + A一直在场、记得前文的开发者
2只有 A离开一段时间、忘了前文的开发者
3只有 B忘了前文，但回复把引用补全了
4只有 C忘了前文，回复补全并按规则重排

采用组内设计：每个参与者读 4 段材料，每段分到一个不同的组，按 4×4 拉丁方轮换，保证每段材料在每个组里出现的次数相同。材料顺序随机。

5.4 任务与交互

可以直接试：打开交互演示。 顶部切换材料和组别；"设计视角"里有三个版本的全文、题目和答案。

每段材料分两步：

  1. 标出看不懂的句子。 回复按句子显示。参与者点击看不懂的句子，再选一个原因：不知道指什么 / 不懂这个词 / 不知道为什么这么做 / 不知道要我做什么。四个原因分别对应缺前文、缺专业知识、缺理由、缺下一步。
  2. 回答 6–7 道选择题。 1 道行动题（"你现在第一件事做什么"），4–5 道远引用题（每道考一个 AI 起的名字，分测试题和对照题），1 道注意力检查题（答案在三个版本里都直接写着）。每道题都有"不知道"选项，选项顺序随机。

5.6 参与者与样本量

  • 参与者： 写过代码的人，按"偶尔写 / 每周写 / 每天写"记录背景，并记录是否用过 AI 编程助手。
  • 预实验： 8 人（拉丁方每行 2 人），用来检查材料、题目和页面。
  • 正式实验： 暂定 40 人。用预实验估出的效应大小做功效模拟之后，再确定最终人数，并在预注册里写明。

5.7 分析计划

  • 主模型： 混合效应逻辑回归，因变量是每道题是否答对，固定效应是组别，随机效应是参与者、材料和题目。
  • 计划比较： 组 1 对组 3（H2a）；组 3 对组 4（H3）；组 1 对组 2 作为操作检查。
  • "以为懂了"： 在组 1 和组 2 之间比较比例（H2b）。
  • 阅读时间： 对数变换后用混合效应线性模型，比较组 3、组 4 相对组 1 多花的时间。
  • 所有分析在正式收数据之前预注册（OSF 或 AsPredicted）。

6. 改进方法与产品方向

如果假设成立，改进方法很直接：只把距离远的引用说全，近的保持原样。 全部说全会让回复变啰嗦；按距离选择性补全，有望用更少的字数换到接近全部补全的效果。第二轮实验会比较"全部补全"和"按距离补全"。

对应的产品是一个 Claude Code hook：记录开发者看过什么、什么时候看的，在 AI 回复显示之前，检查其中引用的名字距离开发者上次看到有多久，超过阈值就自动补一句说明。这个 hook 也可以作为论文中改进方法的实现。

7. 伦理与隐私

  1. 正式实验在学校 IRB 审批（或豁免认定）之后才开始收集数据。
  2. 参与者看到的材料全部是编写的，不含任何真实会话内容。
  3. 收集的数据不含姓名，只记录昵称、写代码频率、答题和标注结果。
  4. 第 4 节的真实会话分析只在本机进行，只报告汇总数字。
  5. 预实验只用来改进材料和页面，数据不进入论文。

9. 风险与局限

  1. 会被认为"就是去语境化"。 回应：本研究只补全距离远的引用；对象是对话里 AI 的回复；用理解题而不是偏好来检验。
  2. 和约定形成研究的结论方向相反。 指代游戏里 LLM 保持啰嗦，本研究说 AI 直接用名字。需要在实验一里同时记录模型什么时候啰嗦、什么时候只用名字。
  3. 文献检索还差 ACM DL 全文检索。
  4. 对话是编写的。 最后一条回复是模型真实生成的，但前面的对话是编写的，可能不够像真实会话。缓解办法：请经常用 Claude Code 的开发者盲评，判断材料里的回复是否像真实 AI 写的；同时用第 4 节的真实数据作为补充证据。
  5. 补全版更长。 B 比 A 长 0–23%，理解更好可能部分来自信息更多。阅读时间会作为成本一起报告；对照题（A 里已经解释的名字）也能帮助区分"信息更多"和"补全了引用"。
  6. 组 1 的遗忘比真实情况轻。 组 1 读完对话马上答题，间隔只有几分钟。真实场景里间隔常常是几小时。所以组 1 的结果偏乐观，如果组 1 仍不如组 3，结论只会更强。
  7. 初步证据来自一个人的数据。

10. 需要的帮助

  • 老师： 对研究问题、假设和实验设计的意见；是否愿意指导这项研究，或作为 IRB 申请中的指导老师。
  • 朋友（写代码的）： 参加 20 分钟左右的预实验；帮忙判断材料里的 AI 回复像不像真的。
